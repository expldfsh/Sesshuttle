# 0.7.2 本机验证记录

0.7.2 解决「Codex 程序」指向启动脚本、程序不可用或快速验证失败时用户无从下手的问题。同步格式、加密、云端布局和导入的身份校验都没有改变：快速验证和原生导入仍只信任真实的可执行文件，验证结果仍绑定到该文件的身份。所有开发期测试只使用临时目录中的合成数据、仅监听回环地址的模拟 S3 和本机应答服务；没有读取或写入真实 `~/.codex`、真实项目或真实 R2。

## 问题与修法

**根因：自动检测把用户带进死路。** macOS 的 ChatGPT.app 中 `codex-cli/bin/codex` 是启动脚本，检测却推荐它，而快速验证拒绝脚本（`runtime_launcher`）。提示又引用了不存在的按钮「编辑路径」，且只有一个必然失败的「重新快速验证」。

- `core/runtime.mjs` 的 `executable()` 识别 `ChatGPT.app`、`Codex.app` 的 `Contents/Resources/codex-cli/bin/codex`，改用同一应用包内的 `CodexCLI.app/Contents/MacOS/codex`。必须同时满足：启动脚本以 `#!` 开头，目标是普通文件、不以 `#!` 开头，`realpath` 后仍在同一应用包内。身份（`file`、`key`、`script`）基于真实程序；用户配置的路径不变。
- 启动脚本的限制没有放宽：脚本仍不能作为快速验证和导入的身份。导入路径上的 `NativeClient` 都使用 `identity.file`。
- 选择或编辑路径后立即检查（`inspectBinary`），打开页面和弹窗不检查。`appStatus` 只读文件头和已保存状态，新增 `launcher`。
- 修复按钮「选择 Codex 程序…」「改用 <路径>」只改写路径草稿，不保存、不运行快速验证。macOS 的文件选择窗口可以进入 `.app`。
- 文案中的界面名称改为 `{@key}` 占位引用，由 `scripts/check-locales.mjs` 校验。

## 用户验收

2026-11-08 用户验收通过。验收项目如下：

1. **macOS 文件选择**：在「本机应用与项目」的 GPT 桌面端卡片点「选择」，核对窗口能进入 `ChatGPT.app` 内部，并定位到当前路径所在目录；路径为空时定位到 `ChatGPT.app/Contents/Resources`。
2. **真实 ChatGPT.app 的自动解析**：把 GPT 桌面端的 Codex 程序设为 `/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex`，核对显示「实际使用：…/CodexCLI.app/Contents/MacOS/codex」；或点「检测本机 Codex 环境」，核对直接推荐真实程序并注明由启动脚本解析。再点「开始快速验证」。
3. **无法解析的脚本**：把路径指向任意自写脚本，核对状态「需要选择 Codex 程序」、提示和修复按钮；点按钮选择真实程序后，出现「未保存」栏和「开始快速验证」，没有自动保存或验证。
4. **Arch 上的 GPT 桌面端布局**：按 [Linux 验收清单](../guides/zh-CN/linux-acceptance.md) 第 1 步核对检测结果是真实程序（`file <路径>` 显示 ELF）。如果是脚本，请反馈路径和脚本内容，再决定是否增加解析规则。
5. **Mac ↔ Arch 换机往返**：两端更新后各做一次上传和导入，并在 Debian / Ubuntu 上安装 `.deb` 并启动一次。
