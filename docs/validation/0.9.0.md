# Sesshuttle 0.9.0 Windows 11 x64 免安装版验收

## 交付方式

解压 `sesshuttle-0.9.0-win-x64.zip`，双击 `Sesshuttle.exe`。首次选择数据位置并核对完整路径，以后双击同一个程序即可。选择标准目录 `%USERPROFILE%\Sesshuttle Data` 时，程序直接从该目录读取数据。选择其他位置时，程序在个人主目录创建可见的 `Sesshuttle Location.json`，用它记住路径和文件夹标识。设置会显示其位置。

Windows 普通账户读出的交付 ZIP 的 SHA-256 为 `f96d63929eb96df1255c33fabcfd8b7c6a7354fc1570fcda547502fdcef12b0c`。ZIP 为 159,642,286 字节。两个可执行文件均为原生 x64 图形程序，ZIP 完整性检查通过。本地包未做代码签名。使用时保留整个解压目录。

## Windows 验收环境

验收在 Windows 11 Enterprise Evaluation x64（10.0.26300.0）中进行，使用独立虚拟磁盘和普通本地测试账户。消息、项目、凭据及模型回复均为合成测试数据，网络只连接本机验收服务。安装包从压缩文件解出后直接运行。AppData 对比覆盖 Roaming、Local、LocalLow，以及账户中额外存在的分支。

首次验证 Codex CLI 0.166.0 时，Windows 在约 34 秒完成样本导入，约 48 秒完成续聊和历史核对。此前的 30 秒上限会在导入中途触发。本版将 Windows 首次验证的等待上限调整为两分钟，保留原有校验和取消操作。

## 首次选择、重开与卸载

程序解压在 C 盘的“文档”，数据选在独立的 D 盘，目录名包含 `Chat 中文 100%`。所有启动均使用普通账户，无需管理员权限。

| 实际操作 | 观察结果 |
| --- | --- |
| 首次打开并取消 Windows 文件夹选择框 | 程序退出，数据目录和主目录位置记录均未创建 |
| 再次打开，选择 D 盘并确认完整路径 | 界面正常显示，数据库出现在 `Chat 中文 100%\Sesshuttle Data\data`，主目录位置记录的标识与数据目录一致 |
| 关闭，再点原来的程序图标 | 直接进入主界面，数据库设备标识相同 |
| 把解压目录搬到 `App 中文 100%` 后双击 | 仍然使用同一份数据库。另一次在窗口尚未载入时关闭，程序正常退出 |
| 退出后，删除解压目录、所选数据目录和可见的位置记录 | Windows 确认三处均已移除 |

普通账户首次运行前和卸载后的 AppData 清单均为 **7,431 项**，四次清单都没有不可读目录。卸载时比基线多出一个微软 TokenBroker 缓存文件，少了一个已存在的 `Local/Temp/BIT9CE8.tmp` 文件。另有 12 个原有文件发生变化，分别属于微软拼写词典、OneDrive、Windows WebCache 和系统 WebView。程序目录、所选数据目录和主目录的位置记录均已删除。

跨平台续聊、旧数据迁移和密码解锁完成后，清单为 7,438 项，相比初始清单新增 11 项、减少 4 项。新增项中 10 项在微软 OneDrive、TokenBroker 或 Windows Web Experience 的目录中。对另外一个位于 `Local/Temp` 的零字节文件，Windows 返回的唯一占用进程是 `System`（PID 4）。在两次核对中均未发现属于 Sesshuttle 的 AppData 残留。[各阶段 AppData 的逐项差异](0.9.0-windows-appdata.json)

## Mac → Windows → Mac 原生续聊

两台系统均运行官方 Codex CLI 0.166.0。Windows 使用交付 ZIP 的应用执行连接、预览和导入。测试空间提供兼容 S3 的本地服务，模型回复由本地测试服务生成。整个过程使用合成项目和凭据。

| 系统 | 实测结果 |
| --- | --- |
| macOS arm64 发送 | 创建含早期标记和内嵌图片的会话，读取 Mac 工作目录内的测试文件，再加密上传 |
| Windows 11 x64 接回 | 会话标识一致，原图可读，原生项目中能找到该会话。Codex 从保存的工作目录读取了 Windows 独有的测试文件，随后发出新消息并上传。原生记录从 3 轮增至 4 轮 |
| macOS arm64 再接回 | 在新回复前读到 Windows 发回的那条消息和原图，旧标记仍在模型请求中。Mac 核对本机工作目录并继续，记录由 4 轮增至 6 轮，其中一轮为目录核对 |

Windows 通过 Codex 的 `command/exec` 在会话实际记录的工作目录调用系统 `cmd.exe`。另测的 `thread/shellCommand` 未在该评估环境的 30 秒内完成 PowerShell 启动。续聊和图片验证均由原生会话接口完成。

## Windows 的三个续聊入口

在同一普通账户安装了官方 Codex CLI、商店桌面应用，以及 VS Code 和 OpenAI 扩展。用 ZIP 中的正式应用启动检测后，对同一条云端记录，依次验证了三套原生程序、导入项目、点击「继续」及打开的客户端。

| 入口 | 实际版本 | 观察结果 |
| --- | --- | --- |
| CLI | Codex 0.166.0 | 原生终端按会话标识执行 `resume`。完整的收发、图片和后续轮次见上面的往返记录 |
| 桌面端 | 商店包 OpenAI.Codex 26.1111.9664.0，内置 Codex 0.169.1 | Windows 将会话链接交给 ChatGPT。可见窗口属于该包内的 `app\ChatGPT.exe` |
| VS Code | 编辑器 1.147.0，OpenAI.chatgpt 26.51111.21308，内置 Codex 0.169.0-alpha.11.1 | 首次检测时没有 `vscode` 链接关联，应用将会话链接直接交给已安装的 `Code.exe` 并打开其窗口。VS Code 运行后，第二次检测到它已经登记该链接，再次打开成功 |

此测试账户没有登录个人账号。桌面端和编辑器分别验证到本地原生历史、程序交接和实际窗口。真实消息往返通过两端的 Codex CLI 完成。商店桌面端的首次查询用时约 45 秒。Windows 能返回已登记的应用名，即使不公开该应用的可执行路径。VS Code 支持从命令行接收相同的扩展链接。[Electron 应用关联接口](https://www.electronjs.org/docs/latest/api/app/#appgetapplicationnameforprotocolurl) · [VS Code 链接处理](https://code.visualstudio.com/docs/configure/command-line#_opening-vs-code-with-urls)

打开两个第三方客户端后又独立核对了 AppData。从续聊结束时的 7,438 项，到打开客户端后的 8,452 项，再到重复测试后的 8,454 项，主要增量来自 VS Code 和商店版 ChatGPT 的用户资料。文件名检索匹配的六个路径都位于 Windows ConnectedDevicesPlatform 下，包含测试用户的账户名 `SesshuttleQA`，在运行 Sesshuttle 前已经存在。最后一次完整测试也记录了三个入口打开的同一会话标识、两个可见窗口对应的程序路径，以及 AppData 的变化。

复测窗口时，可用 `x86_64-w64-mingw32-g++ -std=c++17 -O2 -static tests/windows/client-windows.cpp -o client-windows.exe` 构建验收工具，并将它的绝对路径作为 `scripts/windows-client-acceptance.mjs` 的第三个参数。
