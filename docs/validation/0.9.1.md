# Sesshuttle 0.9.1 验收

0.9.1 修复对 0.9.0 做代码审查时发现的问题。本轮在 Mac 上开发和核对。Windows 上的运行只有发布工作流里的自动检查，**没有在带桌面的 Windows 电脑上手动验收过**。下面分开列出：本轮核对了什么、哪些结论沿用 0.9.0 的实机验收、哪些改动要等 Windows 上确认。表格里写着「未实测」的项目，指的都是这种手动验收。

## 本版改动与核对方式

| 问题 | 现在的行为 | 核对方式 |
| --- | --- | --- |
| 程序所在文件夹的名字含 `%`、`[`、`]`、`~` 时，窗口只显示「无效操作」；`%` 后跟两位十六进制时页面加载不出来 | 页面按转义后的文件地址加载，请求来源按解码后的路径判断 | 界面回归新增 `location` 组：把应用复制到 `App 中文 100% [x] ~ #1 %41` 中启动。修复前失败，修复后通过。开发构建和 Mac 安装包各跑一遍。单元测试覆盖 Windows 的盘符大小写和共享路径 |
| 「继续」提示「预览后数据或设置发生变化」，刷新也没用 | 数据目录按解析后的路径比较；桌面端和 VS Code 不再比较 Codex 程序路径。设置确实改过时，说明改了什么并给出「本机应用与项目」入口 | 单元测试 3 项；界面回归核对新提示和按钮 |
| 启动器找不到运行组件时无声退出；直接打开运行组件时提示数据文件夹无法识别 | 两种情况都说明该打开哪个文件 | 启动器用与工作流相同版本的 llvm-mingw 编译通过，核对了编译产物中的提示文字。**提示窗口本身没有在 Windows 上看过** |
| 原数据文件夹删除后，每次启动都只能选回原文件夹 | 在选择窗口点取消后，询问是否改用空白数据文件夹 | 选择逻辑移到 `core/folder-choice.mjs`，单元测试 7 项覆盖首次启动、搬动、删除、位置记录损坏等路径。Mac 安装包从图标启动的流程另由 `ui-data-folder` 走了一遍 |
| 快速验证或导入已完成，却因清理临时目录失败而报错；启动时清理失败会让应用打不开 | 删除和重命名在文件被短暂占用时重试；收尾清理失败留到下次启动 | 单元测试用替换后的文件接口模拟占用。**真实的占用只在 Windows 上出现，未实测** |
| 窗口、任务栏和任务管理器显示 Electron 的图标和名称 | 运行组件和启动器都带应用自己的图标和版本信息 | 在 Mac 上打出的 ZIP 中逐项读取两个程序的资源，见下文。**显示效果没有在 Windows 上看过** |
| 连接存储不经过系统代理 | 每个新连接询问系统代理，经 HTTP 代理建立隧道 | 单元测试 3 项：本机代理加本机 HTTPS 服务，含完整的存储读写。Electron 返回的代理格式用固定配置核对过。**没有用真实代理连接过 R2** |
| 英文界面下，已同步对话的「⋯」菜单超出详情面板，点不到「Delete chats…」 | 菜单加宽，放不下时在菜单内滚动 | 界面回归的英文一轮在 0.9.0 上就因此失败，修复后通过 |
| 查看 Git 状态时闪出命令行窗口；带引号的路径被当成没有设置程序；回收站路径分隔符混用；首次选择窗口的语言跟随区域格式；CLI「继续」出错时窗口一闪而过 | 分别修正 | 路径相关的有单元测试。其余几项只在 Windows 上可见，**未实测** |

- `Sesshuttle.exe` 是 x64 图形程序，带应用图标、清单（`asInvoker`、长路径、每显示器 DPI）和版本信息：文件说明与产品名 `Sesshuttle`，版本 `0.9.1`。

- ZIP 共 23 个条目，`resources` 中有 `app.asar` 和 `sesshuttle-start.cjs`，没有多余的构建中间文件。

## 对 0.9.0 验收记录的更正

0.9.0 的记录写着「把解压目录搬到 `App 中文 100%` 后双击，仍然使用同一份数据库」。这一步不可能通过：目录名里有 `%`，页面发出的每个请求都会被拒绝。在 Mac 上用同名目录复现，窗口显示的是「无效操作」和一个重试按钮。验收脚本当时只等待页面里出现任意一个按钮，随后核对的设备标识是首次启动时就写入数据库的，所以没有发现。脚本现在要求出现应用自己的界面（至少五个按钮），搬动后的目录名也改为 `App 中文 100% ~ #1 %41`。方括号留给工作流里的检查，因为 PowerShell 的部分命令会把它当成通配符。

## 沿用 0.9.0 实机验收的结论

以下内容在 0.9.0 上用 Windows 11 x64 实机验收过，本轮没有重做。完整记录和 AppData 逐项差异在 Git 历史中，用 `git show 0a03c25:docs/validation/0.9.0.md` 查看。

- 首次选择数据位置、取消、从原图标重开、卸载后 AppData 中没有属于 Sesshuttle 的残留。
- Mac → Windows → Mac 用 Codex CLI 0.166.0 原生续聊往返，含图片。
- CLI、商店版桌面端和 VS Code 三个入口的「继续」。

本轮改动涉及其中的启动流程、「继续」和快速验证的收尾，所以这些结论对 0.9.1 只能作为参考。

## 工作流中新增的 Windows 检查

发布工作流现在会在 Windows 运行器上解压 ZIP，通过 `Sesshuttle.exe` 用合成数据打开应用并读出对话列表，再把整个程序目录复制到 `App 中文 100% [x] ~ #1 %41` 中打开一次。核心测试中已在 Windows 核对过的文件也在那里运行。

分支第一次推送后（提交 `f6181fd`，[运行记录](https://github.com/expldfsh/Sesshuttle/actions/runs/44766233553)），这些步骤在 Windows Server 2025 运行器上的结果：

| 步骤 | 结果 |
| --- | --- |
| 打出 Windows ZIP（含启动器编译、运行组件的图标和版本信息写入） | 通过 |
| 解压后通过 `Sesshuttle.exe` 打开，读出合成对话 | 通过。应用报告版本 0.9.1、3 条对话，两套字体已加载 |
| 把程序目录复制到 `App 中文 100% [x] ~ #1 %41` 后通过 `Sesshuttle.exe` 打开 | 通过 |
| 已在 Windows 核对过的核心测试（`npm run test:windows`，21 项） | 通过 |
| 其余核心测试（只报告，不阻止发布） | 122 项中 92 项通过、26 项失败、3 项跳过，另有一个测试文件没有结束 |

这是本轮改动第一次在 Windows 上实际运行：新的启动器、启动脚本、写入了图标的运行组件和特殊目录名的修复都经过了这条路径。对话框、图标显示、原生应用续聊等仍然需要在有桌面的 Windows 电脑上确认。

失败的 26 项逐条看过，都是测试自身对 POSIX 的假设，没有指向产品代码：权限位断言、用 `sh` 脚本或没有 `.exe` 后缀的替身充当 Codex 程序、用符号链接模拟占用、用 `/` 拼接后与规范路径比较、清理钩子在数据库关闭前删除文件，以及只适用于 Linux 和 Mac 的检测用例。没有结束的那个文件是删除流程的测试，失败后没有关掉它启动的本机服务。这一步当时没有单独的时限，把所在任务拖到了 20 分钟的上限并被取消；随后的提交给它加了 5 分钟时限，并让测试运行器在测试结束后强制退出。

## 需要在 Windows 上确认的步骤

1. 用 `release/sesshuttle-0.9.1-win-x64.zip`，或推送分支后从 Actions 下载工作流打出的 ZIP。解压后双击 `Sesshuttle.exe`。看到「Windows 已保护你的电脑」时点「更多信息 → 仍要运行」。
2. 第一次选择数据位置的窗口出现在最前面，语言与 Windows 显示语言一致。
3. 标题栏、任务栏和任务管理器中显示 Sesshuttle 的图标和名称。
4. 把解压目录改名为 `App 100% [x]` 后再打开，主界面正常。
5. 退出后双击 `sesshuttle-runtime.exe`，提示改为打开 `Sesshuttle.exe`。把 `sesshuttle-runtime.exe` 临时改名后双击 `Sesshuttle.exe`，提示无法启动并列出缺少的文件。
6. 退出后删除数据文件夹再打开：先提示找不到原文件夹，在选择窗口点取消，确认改用空白数据文件夹，然后可以选择新位置。
7. 检测 Codex 应用，对一条云端对话做导入，在 CLI、桌面端和 VS Code 中各点一次「继续」。CLI 应打开终端窗口并进入会话。
8. 在「本机应用与项目」把某个应用的 Codex 数据目录改成末尾多一个 `\` 的写法并保存，已导入的对话仍然可以「继续」。
9. 粘贴一个带引号的 Codex 程序路径，引号自动去掉。打开某个项目的 Git 状态，没有命令行窗口闪过。
10. 如果这台电脑通过系统代理上网，在只开系统代理的情况下「测试连接」通过。
